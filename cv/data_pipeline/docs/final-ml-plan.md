Итого 62 фото, 61 с описанием состояния. Корректный GPS извлечён из одного

XLSX описания важнее упрощённого класса папки: механические повреждения могут
сопровождаться дефектами ЛКП, а описание фото из группы ЛКП может упоминать
нарушение целостности другого объекта. Не сводить описание к эксклюзивному
классу без просмотра человеком. Не передавать имя папки/описание/имя файла
модели как вход: это утечка ответа. Они служат только эталоном и отчётом.

## Что должно выдавать решение

По актуальному DOCX: входное фото → объект → признаки состояния → перечень
для дополнительной проверки/ремонта; демонстрация на тестовых данных,
интерфейс/таблица результатов, короткая архитектура и путь к автомобильной
камере. По условиям сдачи из сообщения пользователя: PDF/PPTX по брендбуку,
слайд «Дополнительные материалы» со ссылками на код, прототип и документацию,
доступными экспертам. Упоминание колодцев/опор в контексте DOCX не делает
выданные фотографии разметкой столбов.

## План за хакатон

1. В Marimo просмотреть реальные фото вместе с исходным XLSX-описанием;
   отметить неоднозначные/смешанные случаи. Отдельно определить задачу:
   тип объекта (РЩ/ТКШ) и состояние (норма/МП/ЛКП/неизвестно).
2. Без bounding boxes начать с классификации/поиска похожих примеров,
   а не выдавать рамки детектора столбов за обнаружение дефектов шкафа.
3. Первый baseline: признаки существующего локального backbone, косинусный
   поиск похожих размеченных фотографий, предварительный класс по соседям.
   Это retrieval/few-shot baseline, не дообученная модель и не вероятность
   дефекта. На таком количестве данных всегда нужна проверка человеком.
4. Оценивать leave-one-object-group-out: исключить сам запрос, одинаковые
   SHA-256 и весь объектный идентификатор. Показать confusion matrix,
   macro-F1, ошибки и число примеров; не обещать качество на новых маршрутах.
5. Следующий эксперимент при наличии GPU/времени: предобученный визуальный
   encoder, замороженная основа + маленькая классификационная голова;
   одинаковые групповые splits, небольшой размер изображения, ранняя
   остановка, без агрессивных аугментаций мелких дефектов. Для локализации
   дефектов сначала вручную размечать объекты/зоны, потом дообучать детектор.
6. В продукте отделять модельный результат от рекомендации. Неуверенный или
   неизвестный случай → «проверить». Даже высокая similarity/confidence не
   означает срочный ремонт; правила критичности согласуются с экспертами.

## Воспроизводимая подготовка без Git-фотографий

Скачать два ZIP в отдельное хранилище, затем:

```bash
uv run --project cv/data_pipeline python -m mgts_data_pipeline.final_materials \
  --archive /path/doc-1795639519.zip \
  --archive /path/doc-1795639569.zip \
  --output /new/path/mgts-final
```

Для явной загрузки с проверкой зафиксированных SHA-256 вместо двух
аргументов `--archive` можно передать `--download-root /path/organizer-zips`.
Валидный кэш переиспользуется, несовпадающий хеш останавливает операцию.

Команда сохраняет исходные байты фотографий и provenance JSON, связывает
таблицы по папке + stem, не исполняет вложенные файлы, не создаёт рамки,
не назначает случайный split и не перезаписывает существующий каталог.
Данные организаторов не публикуются автоматически на Hugging Face:
разрешение на перераспространение неизвестно. На стенде они лежат вне Git
в существующем archive volume; контейнерные пути описаны в README.

## Ограничения

- Старый checkpoint `odn_pole` обучен искать столбы. Использование его
  признаков — слабый baseline с переносом домена, а не обученная экспертиза
  коррозии/деформации. Нельзя выдавать его детекции за дефекты РЩ/ТКШ.
- Набор очень мал; нет честной независимой тестовой выборки от организаторов.
- Для предоставленных фото ещё не подтверждена связь идентификатора файла
  с адресом реального объекта. GPS камеры/фото не равен автоматически
  координате объекта.
- Работа на случайном кадре с движущегося автомобиля пока не доказана.
- Фото может показывать несколько объектов, а метка относится к одному:
  дальнейшее улучшение — ручные ROI/разметка и отдельная проверка.

### Первый измеренный результат

Локальные признаки, 5 ближайших соседей, 61 размеченное фото. Проверка по
60 группам: идентификатор и точные дубли запроса исключены из эталонов.
Состояние: **34/61** совпадений (55,7%), macro-F1 **0,550**. По классам:
норма 15/20, МП 11/21, ЛКП 8/20. **9 из 41 повреждённых** ошибочно получили
«норма». Тип шкафа: 29/61. Это не независимый тест на новых маршрутах.
Отрицательное предсказание не снимает объект с ручной проверки.

Для очереди диспетчера (положительный класс = любое повреждение, та же
матрица, без переобучения): TP 32, FP 5, FN 9, TN 15; precision 86,5%,
recall 78,0%, F1 82,1%. Ещё 13 фото ошиблись подтипом повреждения, но попали
в правильную очередь. Per-class precision / recall / F1: ЛКП 47,1 / 40,0 /
43,2%; МП 55,0 / 52,4 / 53,7%; норма 62,5 / 75,0 / 68,2%. Это метрики
одного классификатора снимков, а не mAP детектора и не метрики маршрута.

### Повторить измерение

Из корня репозитория, при доступных manifest/фотографиях и доверенном локальном checkpoint:

```bash
uv run --project cv/data_pipeline --extra inference python -m mgts_data_pipeline.cabinet_baseline build /path/mgts-final/final-materials.json /new/path/reference.json cv/ml/best.pt
uv run --project cv/data_pipeline --extra inference python -m mgts_data_pipeline.cabinet_baseline evaluate /new/path/reference.json --top-k 5
```

В редакторе уже подключён готовый индекс. Ничего строить для демонстрации
не требуется. Для нового эксперимента укажите **другой** путь, чтобы не
перезаписать готовый индекс. На новом кадре модель предлагает похожие
эталоны, класс и ручную проверку; образцы МГТС сравниваются отдельно от их исходных подписей.
